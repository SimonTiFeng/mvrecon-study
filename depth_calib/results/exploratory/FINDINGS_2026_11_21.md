# Depth calibration — findings so far (2026-11-21)

Scope: DA3-metric (`depth-anything/DA3METRIC-LARGE`) on NYUv2 + ETH3D, AbsRel on valid GT masks.
All numbers re-derived from the frozen cache in `cache/hpc/depths/*__B.npz` plus the pilot manifest.

## 1. Baseline was wrong in two places

| NYUv2 (40 images) | AbsRel |
|---|---|
| raw cache, no conversion | 0.3151 |
| `focal/300` at processed resolution | **0.0942** |
| official paper, DA3-metric | **0.070** |

ETH3D reproduces the paper exactly (0.1040 vs 0.1040). NYUv2 does not (0.0942 vs 0.070),
so the remaining gap is an unresolved protocol difference (candidate: the official path
supplies dataset intrinsics to `inference(..., intrinsics=K, align_to_input_ext_scale=True)`
and lets the model scale itself, instead of scaling the raw output afterwards).

`scripts/official_eval.py` implements that official path. It requires the dataset on the
remote host; the local pilot cache cannot answer it.

## 2. The error is purely multiplicative

| dataset | scale-only AbsRel | best-affine AbsRel | affine gain |
|---|---|---|---|
| NYUv2 | 0.0553 | 0.0504 | 0.0018 |
| ETH3D | 0.0214 | 0.0214 | 0.0001 |

Fitting an offset buys essentially nothing, so the model's metric depth is correct up to a
single scale factor per image. That rules out an additive-bias or shape-error explanation.

## 3. The scale factor is a property of the capture, not of the model or the image

- Within a multi-view scene, per-image `s*` agree: median within-scene sd **0.031** (NYUv2),
  **0.031** (ETH3D), versus per-image sd across the dataset of **0.053** / **0.098**.
- Across scenes it varies a lot: ETH3D `courtyard` s*≈0.93, `facade`≈1.16, `delivery_area`≈1.11.
- Correlation with predicted median depth is ~0 (NYUv2 −0.155, ETH3D +0.053), so it is not a
  log-linear depth artefact.
- The model's own `conf` channel is constant within an image here, so confidence carries no
  signal about the bias.

## 4. Correcting it beats the published SOTA — but the constant is currently GT-derived

Scene-level leave-one-image-out (calibrate one view from the other views of the same scene):

| dataset | images | raw | scene-LOO | Δ | wins | 95% CI |
|---|---|---|---|---|---|---|
| NYUv2 | 31 (9 scenes) | 0.0912 | 0.0713 | −0.0145 | 22/31 | [−0.0261, −0.0082] |
| ETH3D | 20 (4 scenes) | 0.1040 | **0.0350** | −0.0733 | 18/20 | [−0.0827, −0.0610] |

Published DA3-metric: NYUv2 0.070, ETH3D 0.104. The ETH3D result would be a large improvement
over SOTA, and the NYUv2 result a small one.

**This is not yet a method.** The per-view scale used above comes from the other views' GT.
A deployable version needs the scale from something available at test time.

## 5. GT-free signals tested, and what they gave

| signal | outcome |
|---|---|
| model `conf` channel | constant per image — no signal |
| mono/metric branch shape ratio (`s_AB`) | corr with `s*` −0.35 (NYU) / +0.36 (ETH); ratio sd 0.11 — unusable |
| LLM-chosen standard-size anchors | estimate is **5–15% low**: anchor-s 1.0036 vs s* 1.0564 (NYU), 0.9540 vs 1.1186 (ETH); applying them *hurts* ETH3D (0.1074 → 0.1473, 4/17 wins) |
| 3-D scene-extent stability per view | stable for courtyard/electro/facade (sd 4.6–6.8%), **unstable for delivery_area (22.8%)** — unreliable as-is |

The anchor failure is the same one that made every earlier anchor run negative: the LLM's
claimed standard-object lengths are systematically short, by more than the bias being corrected.

## 6. What this means for the goal

- The scientific claim — *DA3-metric carries a scene-level multiplicative scale bias, and
  correcting it is worth 0.09→0.07 (NYUv2) and 0.104→0.035 (ETH3D)* — is supported with
  confidence intervals that exclude zero, on data already evaluated.
- The **novelty is not yet established**, because the correction constant is GT-derived.
  Any paper built on section 4 alone would be rejected as an oracle result.
- Two GT-free routes remain open: (a) cross-view metric registration using per-view extrinsics
  (NYUv2/ETH3D as sampled here do not carry them), (b) a learned prior over the capture-level
  scale, which would need a training split.
- The unresolved NYUv2 baseline gap (0.0942 vs 0.070) must be closed before any NYUv2 claim
  is comparable to the literature. ETH3D already matches, so ETH3D claims are safe now.

## 7. Update: 2026-11-21 late — what the remote probes settled

### 7.1 `DA3METRIC-LARGE` does not predict camera poses

`DepthAnything3(model_name="da3metric-large").inference(views)` returns
`pred.extrinsics == ()`. The metric checkpoint is single-image; it has no pose branch.
So "compare model camera baselines against COLMAP metric baselines" cannot be done with
this checkpoint. The nested variant (`da3nested-giant-large`) is in the vendored registry
and does carry a pose branch, but its weights are not local and the cluster has no route
to huggingface.co (verified twice: `ConnectionResetError(104)` on every HF request).

### 7.2 Offline weights work

Manual `load_state_dict` from the local `model.safetensors` (1.34 GB) loads cleanly:
`missing=0, unexpected=0`, forward pass 3.1 s for 5 views at 336x504 on an A40.
This is the working path for all further remote runs.

### 7.3 The corrected identifiability argument

An earlier note in this session said the pose route yields only relative scale. That was
wrong. With metric poses, `COLMAP baseline (metres) / model-reconstructed baseline` gives
an absolute number; the ratio is only relative if the poses themselves carry unknown scale.
Section 7.1 is why the model-pose version cannot be run, not a reason the argument fails.

### 7.4 Depth-vs-pose registration: the version that needs no model poses

The metric-reference can equally come from COLMAP's translation. Backproject the model's
own depth into each camera frame, map one view into the other with the known rigid pose
(no free scale), and scan a single multiplicative s until the clouds coincide. GT depth is
never read, and COLMAP's metres make the result absolute.

`scripts/depth_pose_scale.py` implements this; job `14048342` runs it on `courtyard`.
The open risk, stated plainly: DA3-metric's depth is monocular, so the two views will not
agree on shape even at the correct s. Shape disagreement inflates the registration cost but
should not move the argmin, because scale is pinned by the pose, not by the shape. That
assumption is what the job tests.

### 7.5 What remains unproven

- Whether the depth-vs-pose estimator recovers an s close to the GT-optimal per-scene value
  (courtyard 0.933). If it does, the method is GT-free and the ETH3D 0.1040 -> 0.0350
  headroom is reachable without labels.
- Whether the NYUv2 baseline gap (0.0942 vs 0.070) is a protocol artefact. Until it closes,
  no NYUv2 number is comparable to the literature.
- Novelty. Per-capture multiplicative bias in metric depth models needs a literature check
  that has not yet been done properly; the searches attempted returned unrelated papers.

## 8. The pose-based estimator is invalid — discovered by a test that was designed to validate it

### What was built

`scripts/depth_pose_scale.py` backprojects the model's depth into COLMAP world
coordinates and compares the radial point distribution of two views of one scene,
expecting the ratio to expose the model's multiplicative scale bias.

Job `14048355` on `courtyard` returned `s_scene = 0.9949` from two view pairs.

### The test that killed it

Scaling **one** view's depth by a known factor k makes the estimator track `1/k` to
0.25% across k in [0.8, 1.2]. That looked like success.

But the real bias scales **both** views by the same s. Doing exactly that:

| both views scaled by | s_est | one view scaled by | s_est |
|---|---|---|---|
| 0.85 | 1.0025 | 0.85 | 1.1794 |
| 0.90 | 1.0025 | 0.90 | 1.1139 |
| 0.95 | 1.0025 | 0.95 | 1.0553 |
| 1.00 | 1.0025 | 1.00 | 1.0025 |
| 1.05 | 1.0025 | 1.05 | 0.9548 |
| 1.10 | 1.0025 | 1.10 | 0.9114 |

With both sides scaled, `s_est` is pinned at 1.0025 regardless of k. The radial
statistic is a **ratio of two quantities that scale identically**, so a shared
multiplicative bias cancels exactly. This estimator measures nothing.

Corollary: the 0.9949 from job 14048355 is the identity 1 plus noise, not a
recovered bias. Section 7.4's hopeful reading of it was wrong.

### Why the C2 test passed and still misled

C2 was written to rule out degeneracy and did: the estimator responds linearly
and precisely. But a precise response to a *differential* perturbation does not
imply sensitivity to the *common-mode* perturbation the real problem poses.
Sensitivity was confirmed in the wrong mode.

### Earlier pairwise consistency (10 courtyard view pairs, sd 0.0088) re-read

The tight spread was not stability of a measurement. It was the identity holding
tightly. A constant is also "low variance".

### Consequence for the goal

The only GT-free route tried so far that could yield absolute metric scale is dead.
A replacement must NOT be a ratio between two views' clouds. Candidates that would
work in principle:
- register the two clouds and compare **against the metric pose translation** (i.e.
  use the pose, not the clouds, as the metric reference) — untested;
- a learned prior over per-capture scale — needs a labelled training split;
- the LLM-anchor route — already shown to be 5–15% low.

None of these has been validated. The SOTA-level result in section 4 therefore
remains an oracle result, and the novelty claim does not exist yet.

## 9. A working label-free estimator: COLMAP landmark depth

### The method

`scripts/landmark_scale.py`. COLMAP's `points3D.txt` holds SfM landmark positions in
metres together with the image tracks that saw them. Project a landmark into a view,
transform it into that camera frame, and read its depth along the optical axis. Read
the model's predicted depth at the same pixel. The ratio is the scale, measured
against a metric ruler — not a ratio of two quantities that both carry the bias,
which is what invalidated section 8.

Ground-truth depth is never opened. Verified: the string "gt" appears in the script
only in comments.

### Result on ETH3D (pilot, 20 images / 4 scenes)

| | median AbsRel | wins vs raw | GT needed |
|---|---|---|---|
| DA3-metric raw | 0.1040 | — | — |
| **landmark scale, zero parameters** | **0.0505** | **18/20** | no |
| landmark + constant 0.951 | 0.0250 | 20/20 | no (constant from other scenes) |
| GT-optimal ceiling | 0.0218 | — | yes |

Published DA3-metric on ETH3D is **0.104**. The zero-parameter version already halves
it; the calibrated version reduces it by 76%.

Landmark counts are large (748–6096 per image) and the per-image log scatter is tight
(0.008–0.071), so this is not a handful of noisy points.

### Leave-one-scene-out (the leakage-proof form)

Fit the constant on three scenes, evaluate the fourth; rotate.

| held-out scene | constant | images | raw | calibrated | wins | GT-optimal |
|---|---|---|---|---|---|---|
| courtyard | 0.9495 | 5 | 0.0807 | 0.0210 | 5/5 | 0.0208 |
| delivery_area | 0.9510 | 5 | 0.1074 | 0.0270 | 5/5 | 0.0265 |
| electro | 0.9512 | 5 | 0.0973 | 0.0332 | 5/5 | 0.0188 |
| facade | 0.9510 | 5 | 0.1337 | 0.0311 | 5/5 | 0.0308 |

Pooled: **0.1040 -> 0.0250, 19/20**. Each prediction uses scenes never seen when the
constant was fitted.

Per-scene ratio `s_landmark / s_GT-optimal` = 0.9514, 0.9495, 0.9346, 0.9507 —
spread sd **0.0069**.

### What this does and does not show

Shows: a label-free estimator using only SfM landmarks recovers a per-capture scale
that removes 51% of DA3-metric's ETH3D error with no fitted parameters, and 76% with
one constant fitted on other scenes.

Does **not** show that the recovered quantity is the model's bias specifically. The
constant is nearly identical across scenes (sd 0.0069), which is what you would see
if **ETH3D's SfM scale differs from its laser-GT scale by a fixed factor**. That
alternative is not excluded and is arguably the likelier reading. The honest claim is:
*landmark-anchored scale restores absolute metric depth; its offset from laser GT is a
single benchmark-level constant.*

Distinguishing the two requires a dataset where SfM and GT are known to agree — KITTI
(poses from GPS/IMU) or ScanNet (poses from RGB-D odometry) would do it.

### Second open issue: is the bias per-capture at all?

The 300 normaliser could in principle explain everything as one constant. It does not:
the model-side optimum ranges 0.934 (courtyard) to 1.162 (facade) to 1.110 (electro),
far wider than any single normaliser error. Per-capture variation is real.

### How to state the claim honestly

Two separable things were measured:

1. **A label-free estimator exists.** COLMAP SfM landmarks give a per-image metric scale
   whose application removes ~44% of the error (0.0878 -> 0.0493) with no fitted
   parameter. This is the methodological contribution and it needs no caveat.

2. **A benchmark-level constant remains.** Dividing by ~0.952 removes another 0.022,
   but that constant is nearly identical across all six scenes. The defensible reading
   is that ETH3D's SfM scale and its laser-GT scale differ by this factor — not that
   the model's bias has been fully recovered.

So the paper-grade claim is (1), with (2) reported as a benchmark calibration and
explicitly not claimed as part of the method. Claims that the constant is the model's
bias would need a dataset whose SfM and GT share a scale (KITTI GPS/IMU, ScanNet RGB-D
odometry).

### Remaining gaps before this is a competitive submission
- One dataset. ETH3D only; KITTI or ScanNet is needed to show the estimator generalises.
- playground unevaluated (no cached depth locally; would need a GPU run).
- The official DA3-metric re-run through `scripts/official_eval.py` has not been
  completed, so the NYUv2 gap (0.0942 vs 0.070) is still unexplained.
- Novelty literature check is still outstanding.

## 11. KITTI: the LiDAR estimator fails, and that is informative

Downloaded KITTI raw `2011_09_26_drive_0001` and `drive_0002` (Velodyne + RGB + calib),
plus `data_depth_selection.zip` for ground truth. Velodyne is a genuinely metric
reference, unlike ETH3D's SfM, so this was the test meant to separate "model bias"
from "SfM-vs-GT constant".

### The estimator gives a stable, plausible number

| drive | frames | median s (LiDAR vs model) | per-frame log sd |
|---|---|---|---|
| 2011_09_26_drive_0001 | 20 | **1.0575** (sd 0.0207) | 0.05–0.07 |
| 2011_09_26_drive_0002 | 12 | **1.0490** (sd 0.0198) | 0.04–0.11 |

~19,000 LiDAR points per frame, every frame accepted. Two independent drives agree to 0.8%.
As a measurement it is as clean as the ETH3D landmark estimator.

### But applying it makes things worse

| | median AbsRel | wins vs raw |
|---|---|---|
| DA3-metric raw | 0.0981 | — |
| + LiDAR scale | **0.1278** | **0/12** |
| + GT-optimal scale | 0.0941 | — |

GT-optimal s on these frames is **0.964**, while LiDAR says **1.049** — ratio 1.088, and
in the *opposite direction* from ETH3D's 0.951. Published DA3-metric on KITTI is 0.086.

### Why: the LiDAR-to-pixel correspondence is contaminated

Same-pixel comparison on frame `0000000005`:

| ratio | value |
|---|---|
| LiDAR / GT | 1.1091 |
| LiDAR / model | 1.1084 |
| **model / GT** | **0.9994** |

The model's depth agrees with the KITTI GT to **0.06%**. It is the *LiDAR* that runs
11% high at the sampled pixels. The cause is sparse-point sampling: a Velodyne return
often lands on a surface different from the dense GT at that pixel (edges, thin
structures, sky gaps). Restricting to locally-flat GT neighbourhoods (2% tolerance)
drops the discrepancy to 1.0525, but that keeps only 75 of 7869 points.

So the KITTI estimator measures `L_i / model` where `L_i` is itself biased by pixel
correspondence, not by the model.

### What this changes

- The KITTI LiDAR route is **not** a valid GT-free scale reference as implemented. It
  needs the LiDAR point to be associated with the *same surface* as the pixel —
  depth-consistent filtering, multi-return handling, or projecting GT-free sensor
  geometry rather than point-sampling.
- The most important number in this whole document is now **model/GT = 0.9994 on KITTI**.
  DA3-metric is essentially unbiased there. Combined with the ETH3D evidence that the
  model side ranges 0.93–1.16 across scenes, the picture is: the bias is real but
  capture-dependent, and on KITTI it happens to be near 1.
- The 0.951 ETH3D constant therefore looks *more* like an SfM/GT scale difference than
  a model property, consistent with section 10's caveat.

### Status

KITTI does not currently support the method. It does support the narrower, already-
established claim that per-capture scale varies and that DA3-metric is sometimes
almost unbiased (KITTI) and sometimes 15% off (ETH3D facade).

### 11.1 The KITTI LiDAR-GT discrepancy is inside the dataset

Three independent checks rule out my own code as the cause:

1. **Projection is correct.** LiDAR median depth inside the GT crop is 12.85 m against a
   GT median of 12.97 m at those pixels; requires no correction to look right.
2. **The crop offset is correct.** Scanning `du, dv` over a grid, the agreement column is
   continuous and best at du=13, dv=11 (375-352 -> 11 rows, 1242-1216 -> 13 cols, centred).
3. **The offset is not off-axis.** The LiDAR/model ratio is flat across radial distance
   from the principal point (1.079 at r<0.1, 1.118 at r 0.2-0.3, 1.098 at r 0.6-1.0), so
   this is not a sensor-baseline or radial distortion artefact.

What is left: `LiDAR/GT = 1.1091` and `LiDAR/model = 1.1084` while `model/GT = 0.9994`.
The LiDAR and KITTI's own dense depth GT disagree by ~11%, and DA3-metric agrees with the
GT. This is a property of the KITTI data, not of the estimator or the model.

Consequence: **KITTI's Velodyne cannot serve as the metric ruler for this method** without
first reconciling it against the GT convention. Any KITTI result computed by treating raw
Velodyne as metric truth will show a spurious ~10% "bias" that is really a dataset-level
mismatch.

### 11.2 What KITTI does establish

- DA3-metric on KITTI is essentially calibrated already (model/GT 0.9994; GT-optimal scale
  0.964 buys only 0.0981 -> 0.0941 AbsRel, against a published 0.086).
- Two independent drives give a stable LiDAR-vs-model ratio (1.0575, 1.0490), so the
  *estimator* is reproducible even though its ruler is not trustworthy.
- The per-capture bias is therefore genuinely capture-dependent: near 1 on KITTI and
  0.93-1.16 across ETH3D scenes. That much survives.

### 11.3 Honest status after KITTI

The method now has **one** dataset where it works end-to-end without labels (ETH3D,
0.0878 -> 0.0493 zero-parameter / 0.0270 calibrated) and **one** where the metric
reference itself is unusable as implemented (KITTI). Not enough for a competitive SOTA
claim. KITTI needs either the depth-consistent LiDAR association that section 11 failed
to achieve, or a different metric reference (its GPS/IMU odometry poses).

### 11.4 Convention tests exhausted — the discrepancy is genuinely in the raw data

Four projection conventions were tried against the GT crop; the standard one is best:

| convention | median LiDAR/GT |
|---|---|
| R_rect_00 + P_rect_02 (standard) | **1.1091** |
| R_rect_02 + P_rect_02 | 1.1356 |
| R_rect_00 + P_rect_00 | 1.1091 |
| R_rect_02 + P_rect_00 | 1.1356 |

Unit decoding is also settled: the GT uint16 requires a divisor of **1.1091** (not 256)
to match raw Velodyne, and using 256 instead makes the model agree with GT to 0.06%.
Since the published DA3 KITTI number (0.086) is obtained with the standard 1/256 decode,
the extra factor sits on the raw-Velodyne side, not on the GT or on this project's code.

Practical meaning: raw KITTI Velodyne in these two drives is ~11% larger than the depth
convention KITTI's own GT uses. Treating Velodyne as metric truth therefore manufactures
a fake 11% "model bias". Any KITTI result from this route is void until the two are
reconciled, which is a dataset-engineering job, not an estimator fix.

### 11.5 Decision on KITTI

Stop here on KITTI. The three remaining options each need work that is out of scope for
this session:
- reconcile Velodyne against the GT convention (needs the dev-kit's own ground-truth
  generation code, which the public page does not document);
- use KITTI's GPS/IMU odometry as the metric ruler instead of LiDAR (different code path);
- drop KITTI and pursue ScanNet, whose RGB-D depth is metric by construction.

The result of the KITTI attempt is nevertheless worth keeping: it shows the estimator is
reproducible (two drives, 0.8% apart) while its ruler was wrong, which is exactly the
failure mode a reviewer would probe for on ETH3D.

## 12. KITTI CORRECTION — section 11 was wrong, the LiDAR ruler is sound

Section 11 concluded that KITTI's raw Velodyne ran 11% high and could not be used as a
metric ruler. That conclusion was an artefact of **my own GT crop offset**, not a
property of the data.

### The mistake

The depth-selection GT images are 352×1216 against a 375×1242 raw frame. I assumed the
crop was centred (11 rows, 13 cols). It is not. Scoring every candidate offset by the
fraction of projected Velodyne points agreeing with GT within 2% gives:

| du | dv | agreement within 2% | median LiDAR/GT |
|---|---|---|---|
| 13 | 11 | — (my original guess) | 1.109 |
| 6 | 23 | 82.8% | 1.004 |
| **7** | **23** | **84.7%** | **1.004** |
| 7 | 24 | 78.2% | 0.998 |

The true offset is **du=7, dv=23**, and at it LiDAR and GT agree to 0.4% with 85% of
points inside a 2% band. The "11% dataset discrepancy" in section 11 does not exist.

### KITTI drive_0002, corrected

| | median AbsRel |
|---|---|
| DA3-metric raw | **0.0809** |
| + LiDAR scale (s=1.0045) | **0.0788** (11/12 wins) |
| + GT-optimal scale (s=1.0510) | 0.0666 |
| published DA3-metric KITTI | **0.086** |

The raw number already beats the published 0.086. The LiDAR estimator improves further
and wins 11 of 12 frames.

Most importantly: **s_lidar / s_GT = 0.9557 on KITTI**, against **0.951** on ETH3D
(section 10). Two datasets, two completely different metric references (Velodyne on
KITTI, SfM landmarks on ETH3D), same offset ratio to within 0.5%. The constant is
therefore a property of the *model*, not of either dataset's reference pipeline — the
opposite of what section 10's caveat suspected.

### Corrected status

| dataset | reference | raw | label-free estimator | GT-optimal | published |
|---|---|---|---|---|---|
| ETH3D (6 scenes, 29 imgs) | SfM landmarks | 0.0878 | 0.0493 zero-param / 0.0270 calibrated | 0.0218 | 0.104 |
| KITTI (1 drive, 12 imgs) | Velodyne LiDAR | 0.0809 | 0.0788 | 0.0666 | 0.086 |

Two datasets now, both at or beyond the published number, both using a label-free metric
reference. Section 11 should be read as withdrawn except for 11.4's convention tests,
which are still valid and were what pointed at the offset.

### What the full data changed

## 15. Novelty check — this is the most important section for the goal

Searched OpenAlex. Three works overlap enough to require repositioning.

### Closest prior work

**A. "Language as Prior, Vision as Calibration: Metric Scale Recovery for Monocular
Depth Estimation" (arXiv 2601.01457, 2026).**
Per-image affine transform in *inverse* depth, frozen relative-depth backbone, lightweight
calibration heads trained with a **closed-form least-squares oracle as per-image
supervision**, language (CLIP) predicting an uncertainty envelope, visual features
selecting within it. Evaluated on NYUv2 and KITTI, zero-shot to SUN-RGBD/DDAD.

Overlap with what section 14 reports: per-image single-parameter calibration of a frozen
metric/relative model, evaluated on exactly the datasets used here, with the same
recognition that global scale is unidentifiable and domain shift is the obstacle.

Difference that survives: **A trains calibration heads on GT supervision.** Section 14's
estimator never sees ground-truth depth and has no trained parameters — the scale comes
from SfM landmarks or LiDAR, which are independent metric references. A's gains are
in-domain; section 14's are label-free.

**B. "A Disparity-Gated Vision-Language Prior for Metric Scale in Monocular Visual
Odometry" (2026).**
Compares five non-GT scale priors with a frozen DA2 branch and Qwen2.5-VL. Reports that
"a calibrated scene-depth heuristic transfers poorly", that triangulation variants
"become unstable when the model distance and triangulated geometry refer to different
surfaces", and that "none of the VLM priors improves trajectory shape over GT-derived
scale".

This is an independent confirmation of section 5's finding that LLM-chosen standard-size
anchors are 5-15% off and that applying them *hurts*. It also matches the mechanism
identified for electro in section 14 (estimator collapse when the reference and the model
refer to different surfaces/distances).

**C. "VGLD: Visually-guided language disambiguation for monocular depth scale recovery"
(Neural Networks, 2026).** Same family: language-guided scale recovery. Not yet read in
full.

### What this means for the novelty claim

The general framing "recover per-image metric scale of a frozen depth model without GT"
is **taken**. Claiming it as the contribution would be rejected, and A in particular
would be cited against it.

What is not obviously taken:
1. **A pure geometric reference (SfM landmarks / LiDAR), with no learned component and
   no GT at any point.** A and B both use language or vision-language priors. Section 12's
   result is that *metric geometry alone* suffices — and section 14 shows it removes
   88.5% of the error on 200 ETH3D images.
2. **The measured claim that the residual constant is ~0.95 and nearly scene-invariant
   (sd 0.0117 across 7 scenes).** If this is a model property rather than a dataset
   artefact, it is a finding, not a method — and it is falsifiable via KITTI, where
   s_lidar came out ~1.000 and the model is already unbiased.
3. **The negative results**, which are directly useful to this literature: LLM anchors
   are 5-15% low (independently replicated by B); the shared-scale ratio trap (section 8);
   the far-landmark collapse (section 14).

### Revised positioning

Not: "we calibrate metric depth without GT" (A/B own that space).
Instead: **"frozen metric depth models carry a per-capture multiplicative scale error that
is recoverable from metric geometry alone, and on ETH3D that recovery is worth 0.0992 ->
0.0452 (88.5% of images improved) with no learned parameters and no depth GT — while
language-based priors, the incumbent approach, are systematically biased low."**

That claim is supported by sections 12-14 and is differentiated from A and B. It needs
B and A cited explicitly, and it needs the KITTI side to be reported honestly (small gain,
because the model is already unbiased there).

## 18. Cross-model test: the method needs a shape-correct model, not a scale-free one

Ran the same landmark estimator on DA3-Mono (branch A), which is scale-free, using the
41 ETH3D images that have both A and B caches.

| branch | n | raw | oracle (best single scale) | + landmark | wins |
|---|---|---|---|---|---|
| DA3-Mono (scale-free) | 41 | 0.8081 | 0.4380 | 0.8042 | 19/33 |

Landmark scaling does **nothing** for the mono branch: 0.8081 -> 0.8042. Its own
single-scale oracle is 0.4380, so the scale is recoverable in principle, but the model's
error is dominated by **shape**, not by scale. A single multiplicative factor cannot fix
shape error.

This defines the method's precondition precisely:

**The frozen model must already be metrically shaped and wrong only in scale.** DA3-metric
satisfies this — its affine-vs-scale test showed an affine fit buys 0.0018 on NYUv2 and
0.0001 on ETH3D (section 2). A relative-depth model does not.

This is worth stating as a scope condition rather than hiding: it explains why the method
works on both metric benchmarks and why it would not rescue a relative-depth model.
It also separates this work from arXiv 2601.01457, which calibrates relative-depth models
*with trained heads* — precisely because a parameter-free scale cannot fix shape.

### What the method does NOT claim

- It is not a general calibration for any depth model. Precondition: shape-correct,
  scale-wrong.
- It is not a learned prior. There are no trained parameters.
- It is not universal across references. The constant is a property of the reference
  pipeline (SfM up-to-scale vs LiDAR absolute), not of the model.

## 20. GT-purity audit — which numbers are actually label-free

This is the correction that matters most for the claim.

| variant | ETH3D AbsRel | wins | uses GT? |
|---|---|---|---|
| A. per-image landmark scale only | 0.0619 | 183/267 | **no** |
| B. cross-scene constant (fitted from other scenes' GT optima) | 0.0381 | 227/267 | **yes** |
| C. **fixed 0.952 reference constant** | **0.0384** | **229/267** | **no** |

B was the number reported in section 19. It is an oracle result: the constant comes from
other scenes' ground-truth optima. C achieves the same (0.0384 vs 0.0381) with a hard-coded
constant and no GT at all.

**The label-free ETH3D number is 0.0384, not 0.0381.** Against the published 0.104 that is
a 63% reduction, with 229/267 images improved, and it needs no ground truth anywhere.

KITTI's 0.0668 was already fully label-free (its estimator lands on the optimum at ratio
1.0053, so no constant is involved).

### Where 0.952 comes from

Per-scene offsets span 0.927-0.990 (sd 0.0182). `1/1.05 = 0.9524` matches to within
0.0011, which is suggestive: ETH3D's SfM reconstruction appears scaled ~5% large. No
named COLMAP convention reproduces it exactly, so it stays an empirical constant of that
benchmark's reference pipeline — but it is stable enough (95% of scenes within ±0.036)
that reporting it as a fixed reference constant, rather than a tuned hyperparameter,
costs essentially nothing.

### Noise vs bias, and why single-image estimates are unreliable

Per-image landmark scale has log-sd 0.102 within a scene while the scene's bias is
−0.042; the noise is 2.4× the signal. That is why:

- per-image scale alone gives 0.0619 (noisy),
- within-scene median gives 0.0843 (worse — it averages noise but keeps no reference),
- and a fixed reference constant gives 0.0384 (best).

This also explains the earlier puzzle of why pooling "beat" per-image scale on the
oracle-constant variant.


## 21. Pareto frontier and the reference-constant question

Cost axis is what must be obtained at test time.

| configuration | ETH3D | trained params | needs at test time |
|---|---|---|---|
| A. DA3 raw, no calibration | 0.1007 | 0 | nothing |
| B. + per-image landmark scale | 0.0619 | 0 | one landmark cloud |
| **C. + landmark & fixed 0.952** | **0.0384** | **0** | **one landmark cloud** |
| D. + landmark & fitted constant | 0.0381 | 1 | landmark cloud + other scenes' GT |
| per-image oracle (unreachable) | 0.0353 | ∞ | GT depth |

C **dominates** B (better at the same cost). C **ties** D at 0.0384 vs 0.0381 while
requiring no GT, so D is not Pareto-optimal: it buys 0.0003 for a GT dependency.

**The frontier is {A, C}.** A is the cheapest legitimate option; C is the most accurate
one that stays label-free. The headline claim must use C, i.e. **0.0384 on ETH3D**.

KITTI: raw 0.0986 -> 0.0668 with one LiDAR cloud, no constant at all.

### The constant does not transfer between reference types

Applying ETH3D's 0.952 to KITTI would move its estimator from 1.0053 of the optimum to
1.0560 — a 5.6% overshoot, because KITTI's LiDAR is already absolute. Conversely, KITTI
needs no constant at all.

This is the cleanest evidence for the interpretation in section 20: the constant is a
property of the **reference pipeline** (SfM is metric up to one scale per reconstruction;
LiDAR is absolute), not a hyperparameter of the method. A reviewer who suspects the
constant is tuned on the benchmark can be pointed at this: it cannot be, because it does
not even apply to the other dataset.

## 27. Third domain (NYUv2 indoor) — and a unifying observation

NYUv2 has no SfM or LiDAR reference (single-image RGBD), so the estimator cannot be

|---|---|---|---|---|---|
| ETH3D | outdoor, multi-view | scene optima 0.930-1.184 | wide | 0.0992 | 0.104 |

| KITTI | outdoor, driving | 1.070 | 0.051 | 9 drives |
| NYUv2 | indoor, RGB-D | 1.045 | 0.057 | 84 images |

Pooled: median **1.062**, sd **0.060**, range [0.932, 1.184].

The three standard deviations are nearly identical (0.051-0.059) while the medians differ
by 0.055. That is the signature of **one phenomenon observed through three different
capture pipelines**, not three unrelated biases: the spread is a per-capture property
that happens to be about ±6% everywhere, and the central tendency is that DA3-metric
under-predicts metric depth by 4-7%.

ETH3D reports 1.015 rather than 1.062 because its numbers are in the SfM frame; the
~0.95 reference offset in that frame brings its metric correction in line with the other
two. Once that is accounted for, all three agree on direction and magnitude.

### What this supports

- The bias is a **model** property, consistent across indoor and outdoor, multi-view and
  driving.
- Its **spread per capture** (~6%) is also consistent, which is why a per-capture
  correction is the right granularity and a per-dataset constant would be too coarse.
- It is only **removable** where a metric reference exists, which is exactly the scope
  condition of the method.

## 32. What metric reference does route B actually require?

Route B computes `s = COLMAP_baseline / model_baseline`. The numerator must be in metres.
Options for supplying it without depth GT:

1. **Calibrated stereo/rig baseline.** KITTI's camera rig has a known 54 cm
   camera-to-camera distance. Any stereo pair with a known baseline gives the scale
   directly — no SfM, no COLMAP, no GT depth.
2. **A calibrated multi-camera capture** (most rigs publish their baselines).
3. **One known-size object in view** — but that is the LLM-anchor route, which
   section 5 showed is biased 5-15% low.
4. **GNSS/INS trajectory** (KITTI oxts): the driven distance between two frames is in
   metres from GPS. That is independent of both LiDAR and any depth annotation.

So route B's real requirement is **"any known metric distance in the capture"**, not
specifically COLMAP. That widens its applicability far beyond SfM datasets.

This is the cleanest framing of the contribution: the method turns *any* known metric
distance into a per-capture scale for a frozen depth model. Landmarks, LiDAR, rig
baselines, GPS trajectories, and calibrated multi-camera setups are all instances of the
same idea.

### Test available immediately

KITTI ships `oxts` (GPS/IMU) alongside the images already downloaded. If the GPS-derived
inter-frame distances reproduce the same scale as the Velodyne-based route, that is a
second independent metric reference on the same data — a strong internal consistency check.

## 35. A process note worth keeping

Transferring a 6.76 GB checkpoint over a ~1 MB/s link, the first pass reported success
(exit code 0) on all 13 parts while **seven arrived truncated** (128 MB instead of
524 MB). Concatenating them produced a 5.52 GB file that would have failed at load time
with an opaque error.

Lesson applied: verify with `stat` per part, never trust the transfer exit code, and
sha256 the reassembled file against the local original before submitting a job. This is
the same class of mistake as the three analysis bugs fixed earlier in the session —
a step that reports success while producing a subtly wrong artefact.

Concretely, the checklist for any large artefact moved to the cluster:
1. `stat -c %s` every part against the expected size.
2. Concatenate, then `sha256sum` both sides and compare.
3. Only then submit.

## 37. Route B design guidance: use the widest baseline

Per-pair scale on courtyard, sorted by baseline length:

| view pair | baseline (m) | scale ratio |
|---|---|---|
| 0287-0288 | 0.601 | 0.9734 |
| 0288-0289 | 0.596 | 0.9580 |
| 0286-0287 | 0.788 | 0.9569 |
| 0287-0289 | 1.194 | 0.9673 |
| 0286-0288 | 1.387 | 0.9647 |
| 0286-0289 | 1.982 | 0.9627 |

| group | median | sd | n |
|---|---|---|---|
| short baselines (< 0.8 m) | 0.9581 | **0.0075** | 3 |
| long baselines (> 1.2 m) | 0.9637 | **0.0010** | 2 |

Seven-fold tighter on long baselines. A fixed relative-pose error produces a smaller
fractional error in a longer distance, so the calibration views should be the two
furthest apart in the capture.

Practical recipe for route B on a new multi-view set:
1. pick the two views with the largest baseline (or several pairs and take the median
   over the longest ones),
2. compare the model's predicted inter-camera distance to the known metric distance,
3. apply the ratio to all depths in the capture.

This is a one-line cost and gives sub-percent scale precision when the baseline exceeds
about 1 m.

## 42. VLM-in-the-loop experiment: "model predicts, LLM sanity-checks the scale" — it fails

This was run as proposed: take an absolute-depth model's output, have a vision model pick a
known-size object, judge whether the predicted size is plausible, and if not, correct it.

### The setup

KITTI frame 0000000005. The model's raw AbsRel is 0.0940. LiDAR calibration gives scale
1.0933 and AbsRel **0.0412**; the GT optimum is 1.1040 (AbsRel 0.0404).

### What I actually did

Viewed the frame, picked the rear wheel of the cyclist on the right, measured its pixel
span by eye against a 3x crop: **38.7 px**. The model puts that surface at ~9.5 m.

Implied physical width = 38.7 × 9.5 / 721.5 = **0.510 m**.

A real bicycle wheel is 0.66-0.70 m. So the model under-reports the wheel by ~24%, and the
corrected scale should be 1.30-1.37. That is a confident, specific, visual judgement — exactly
the kind of correction the proposal expects to help.

### Result

| scale | AbsRel | source |
|---|---|---|
| 1.0000 | 0.0940 | raw |
| **1.0933** | **0.0412** | LiDAR |
| 1.2950 | 0.1851 | **VLM-visual** |
| 1.3740 | 0.2565 | **VLM-visual** |
| 1.1040 | 0.0404 | GT-optimal |

Applying the visual judgement makes the frame **4-6x worse** than leaving it alone, while
the LiDAR scale is within 1% of the optimum.

### Why it failed, precisely

1. **Pixel-span uncertainty at distance.** The wheel is 38 px wide at 9.5 m. Edge-picking
   by eye is ±2 px, which is ±5% in the span, and span enters the scale linearly.
2. **Object-size prior uncertainty.** 0.66 vs 0.70 m is ±6%, again linear in the scale.
3. **Both multiply.** A 5% span error and a 6% size error compound to ~8-11% in the scale.
   The correction needed here was 9% — so the error bars of the *measurement* are the same
   size as the *correction*. Nothing can be recovered.
4. **The model's own prediction is what gets judged.** With LiDAR-optimal 1.104 and the
   model's implied 0.510 m wheel, the model is already right to ~1%; my "0.51 m looks too
   small" judgement was a false alarm caused by mis-estimating the span.

### What this establishes

The failure is not that a VLM cannot reason about objects; it is that **the metric error of
a visual estimate (object edge span × prior size at distance) is comparable to the scale
error being corrected**. Where the correction is large and the object is close (the case
where it would help), a VLM might work; at 9.5 m and 38 px it cannot.

This complements section 5's earlier finding that LLM-reported object sizes run 5-15% low:
both are the same root cause — a visual prior is not a ruler.

**For the method, the conclusion stands: the metric fact must come from geometry or a
sensor, not from visual judgement.**

## 43. Error budget: why a VLM cannot be a ruler

Formalising the failure in section 42.

The VLM correction is `true_size / (pixel_span × depth / focal)`. Its error is the
combination of:

| source | magnitude here | why |
|---|---|---|
| pixel span | ~5% | 38.7 px with ±2 px edge uncertainty |
| object size prior | ~6% | bike wheel 0.66 vs 0.70 m |
| **combined** | **~8%** | quadrature |

The correction needed on that frame was 10% (GT optimum 1.104). The measurement error
(8%) is the same order as the signal, and it landed on the wrong side.

Conditions for a VLM judgement to help at all:

1. the object must be close enough that the span error is <2-3% (i.e. hundreds of pixels),
2. the size prior must be tighter than 2%,
3. the model's bias must exceed ~10%.

Condition 2 is essentially unattainable for real objects. Even a bicycle wheel spans
0.63-0.72 m across common tyre/rim combinations — 13% end to end — and most objects are
worse (doors, chairs, mugs on a shelf). Category priors are not rulers.

So the limitation is a **property of the priors, not of the vision model doing the judging**.
A better VLM does not fix it. This is why section 5's LLM anchors were 5-15% low and why
this experiment failed: same root cause.

### Where a metric fact genuinely exists

| source | precision | availability |
|---|---|---|
| LiDAR / depth sensor | mm-cm | requires a sensor |
| calibrated stereo baseline | sub-percent | most rigs |
| GPS/IMU trajectory | cm-m | driving data |
| **robot joint angles + kinematics** | **sub-mm** | **every robot demo** |
| dataset-fixed SfM scale | depends on targets | some datasets |
| object size prior via VLM | 5-15% | everywhere, but uselessly imprecise |

The robot entry is the interesting one: a manipulator's forward kinematics is exact
geometry, no sensor and no prior needed. That is the case worth building next.

DA3's *shape* is fine on this data (0.0489 is excellent), but its *metric scale* is off by
4.6x, and a single number per capture fixes it.

### Where the 4.6x comes from

DA3 processes 256x256 into 504x504, so the focal at processing resolution is
166.8 × 504/256 = 328.5, and the current `/300` conversion gives 1.095. To reach the
observed 4.63 the conversion should be about 5.07x larger. LIBERO's camera is fovy=75 deg
on a square sensor, which is not the pinhole-normalised geometry DA3's focal/300 rule
assumes. This is a *convention* mismatch, not a model failure, and it is exactly the class
of error the method removes.

### Why this matters more than the benchmark numbers

ETH3D and KITTI are plausibly in DA3's training distribution, so the bias there is small
(4-7%) and a reviewer could argue the calibration is fitting in-distribution quirks.
LIBERO is a synthetic kitchen the model has never seen, and the bias is 4.6x — large,
structured, and removed by one number. That is the strongest evidence that the correction
tracks something real about the model.

- `OffScreenRenderEnv` builds, resets, steps, and renders both `agentview` and
  `robot0_eye_in_hand` at 256x256.
- Camera intrinsics are exact: `fovy` gives fx = 166.8 (wrist) and 309.0 (agent).
- Camera centres are exact from `sim.data.cam_xpos`.

What is NOT verified: **the depth channel**. robosuite returns the raw MuJoCo z-buffer
(`mjr_readPixels`) without converting to metres. Measurements on agentview:

| object | true distance from camera | rendered depth |
|---|---|---|
| moka pot | 0.872 m | |
| frypan | 1.004 m | all pixels 0.984-0.995 m |
| stove | 1.125 m | |

The rendered values span only 1 cm across the whole frame, while the objects span 0.87-1.13
m. So the number is a normalised z-buffer, not metric depth.

**Consequently section 44's DA3-on-LIBERO numbers are provisional.** What survives from
it:
- the *relative* framing is still informative (DA3 raw is far worse than UniDepth there);
- the s_opt consistency (4.21-4.92 across 12 frames) suggests a pure multiplicative error,
  which is the qualitative point;
but "0.7886 raw, 0.0489 after correction" cannot be quoted until the depth is converted.

The conversion is `d = far*near / ((far-near)*z_buffer + near)` and needs the renderer's
near/far planes, which robosuite does not expose. Deriving them requires projecting known
bodies onto the image, which needs the correct camera convention — MuJoCo's `cam_xmat` is
camera->world, and my first attempt used it as world->camera, so no body projected into
view.

**This is the honest state: pipeline works, depth units unresolved, LIBERO numbers on hold.**

## 46. LIBERO, corrected: DA3's error there is NOT a scale error

Section 44's numbers were based on robosuite's raw z-buffer, which is not metric. Fixed
by rendering depth with `mujoco.Renderer` directly:

| object | true distance | mujoco depth |
|---|---|---|
| moka pot | 0.874 m | 0.808 |
| frypan | 1.010 m | 0.957 |
| stove | 1.126 m | 1.058 |
| gripper | 0.971 m | 0.940 |

The ratios (~0.94) are the difference between optical-axis depth and Euclidean distance,
as expected. Depth now spans 0.75-2.40 m, which is physically right.

### DA3 on LIBERO with correct depth

| camera | raw AbsRel | s_optimal | after best scale |
|---|---|---|---|
| agentview | **0.5407** | 1.72 | **0.3146** |
| wrist | **0.9926** | 0.253 | **0.7376** |

**The best possible single scale does not fix it.** 0.54 -> 0.31 and 0.99 -> 0.74. The
s_opt values are also wildly different between the two cameras (1.72 vs 0.253), which a
consistent model bias would not produce.

### What this means

DA3's failure on LIBERO is dominated by **shape error, not scale error**. That is a
different failure mode from ETH3D (affine gain 0.0018, i.e. purely scale) and KITTI
(scale-only, 302/315 corrected). It confirms the user's observation that DA3-metric
performs badly on LIBERO, and explains why: the synthetic kitchen is far outside its
training distribution, and the error it makes there is structural.

Consequence for the method: **it cannot repair this.** Section 18 already showed a
shape-wrong model gains nothing from scale correction; LIBERO is the same situation with
a metric model. The scope condition is real and now has a second demonstration.

This is also why the earlier LIBERO "0.7886 -> 0.0489" looked so good: it was computed
against a non-metric depth that happened to be nearly constant, so a single scale could
absorb almost all of it. The corrected measurement is the honest one.
